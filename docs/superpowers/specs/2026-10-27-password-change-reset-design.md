# Password change and reset design

## Intent

Let users with an email/password account change their password while signed in or recover access through a time-limited email link. After either operation succeeds, invalidate the account's refresh-token sessions.

## Goals

- Change password only after verifying the current password.
- Start password recovery without revealing account existence through HTTP status or response content.
- Use ASP.NET Identity's password-reset token and password policy.
- Send reset mail through the existing durable background-task pattern.
- Revoke all refresh tokens after a successful change or reset.
- Add the corresponding frontend forms and API calls.

## Non-goals

- Setting a local password for Google-only accounts.
- Changing Google sign-in or email-confirmation flows.
- Revoking already-issued access JWTs immediately; they may remain valid until their current expiry (currently 15 minutes).
- Changing password policy or configuring a custom reset-token lifetime.

## Current constraints

- `UserRepository` wraps ASP.NET Identity `UserManager<ApplicationUser>` and currently exposes password sign-in and email-confirmation token operations.
- Profile data currently has no local-password indicator; the profile response will expose `HasPassword` so the frontend can hide password change for Google-only accounts.
- `IEmailService` sends welcome and email-confirmation messages.
- The durable background-task outbox stores a task kind and user ID, and has a dispatcher/job pattern for email confirmation. It does not store arbitrary payloads; the reset token should be generated by the reset email job rather than stored in the outbox.
- Adding a password-reset email job requires extending the database task-kind constraint and adding an explicit dispatcher branch; unrecognized task kinds currently fall through to image resizing.
- Refresh tokens can already be revoked for a user through `IRefreshTokenRepository.RevokeByUserIdAsync`.
- The frontend has login and profile pages, shared API helpers, and existing UI components.

## Approaches considered

1. **Use ASP.NET Identity password operations and reset tokens (chosen).** Add repository methods over `ChangePasswordAsync`, `GeneratePasswordResetTokenAsync`, `ResetPasswordAsync`, and `HasPasswordAsync`. It uses the framework's token purpose, expiry, and configured password policy.
2. **Build a separate password-reset token store.** This offers custom lifecycle control but duplicates token generation, expiry, single-use handling, and persistence that Identity already supplies.

The first approach was selected because it fits the existing `UserManager` wrapper and requires less custom security-sensitive code.

## Proposed behavior

### Change password while signed in

- `POST /api/v1/auth/password/change` requires authorization and accepts `currentPassword` and `newPassword`.
- Resolve the account from the authenticated user ID; never accept a target user ID from the request.
- Expose `HasPassword` in the current-user profile response and show the change-password form only when it is true.
- Call Identity's change-password operation. Return validation errors for an incorrect current password or a new password rejected by Identity's configured policy.
- Run the Identity password update and refresh-token revocation in one database transaction; commit only if both succeed. Use the same serializable isolation level as refresh-token rotation to prevent an overlapping refresh from leaving a new session active.
- On success, the frontend clears the current browser's stored session and returns to login because its refresh token has also been revoked.

### Request a reset email

- `POST /api/v1/auth/password/forgot` is anonymous, rate-limited by the endpoint, and accepts an email address.
- Always return the same HTTP status and response body whether the account exists or not; do not include account-existence details.
- Apply a separate 60-second cooldown keyed by the normalized email before looking up the account. A cooldown hit or limiter failure skips enqueueing and still returns the same accepted response; use a distinct key from email-confirmation resends.
- For a confirmed email account with a local password, enqueue a durable `password-reset-email` task. Do not enqueue for unknown, unconfirmed, or Google-only accounts.
- Extend the task-kind database constraint and route this kind explicitly in `BackgroundTaskDispatcher` to a new reset-email job. Add a no-op implementation to `NoBackgroundTaskQueue` and verify enqueue/dispatch/job routing.
- The job generates an ASP.NET Identity password-reset token when it runs, builds a frontend reset link, and sends it through a new `IEmailService` method. Do not persist the raw token in the task table.
- Put `userId` and token in the URL fragment, following the existing email-confirmation link pattern; the frontend reads the fragment and submits the values in the reset POST body.

### Submit a new password

- `POST /api/v1/auth/password/reset` is anonymous and accepts `userId`, `token`, and `newPassword` from the emailed link/form.
- Apply Identity's reset-password operation. Invalid or expired tokens produce a generic invalid-link response; do not expose account existence.
- Run the Identity password update and refresh-token revocation in one serializable database transaction; commit only if both succeed.
- On success, the frontend clears any current browser session and returns to login.

### Frontend

- Add a “Quên mật khẩu” entry from login and a request form that shows the same confirmation after submission.
- Add a reset form that reads the user ID and token from the email link, accepts a new password, and reports invalid/expired links.
- Add a change-password form to the signed-in profile page with current and new password fields.
- Use existing API helpers, shared UI components, and the app's existing form/error patterns.

## Security and failure behavior

- Reset tokens are short-lived and single-use according to ASP.NET Identity's configured token provider; no custom lifetime is introduced.
- Reset tokens stay in the URL fragment, are safely encoded, and are never stored in the background-task table or sent in the initial page request.
- Rate-limit reset requests and avoid account enumeration.
- Apply both endpoint rate limiting and the per-normalized-email cooldown before account lookup; fail closed if the email cooldown service is unavailable without changing the public response.
- The account-existence guarantee covers response status and content; response timing is not normalized in this scope, so the lookup/outbox branches may have measurable timing differences.
- Keep password policy enforcement in Identity so both password paths follow the same policy.
- Commit the password update and refresh-token revocation together so a failed revocation cannot leave the new password paired with active refresh sessions.
- Because access JWTs are stateless, revoking refresh tokens does not immediately invalidate JWTs already issued to other devices; their remaining lifetime is bounded by token expiry.

## Acceptance checks

- Correct current password changes the password; wrong current password does not.
- Unknown, unconfirmed, and Google-only email requests receive the same HTTP status and response body and do not send mail.
- Repeated requests for one normalized email within the cooldown do not enqueue another email and return the same status/body; the password-reset cooldown does not block email-confirmation resends.
- A valid reset link changes the password once; expired, malformed, or reused links fail without changing it.
- A new password that violates Identity policy is rejected through both flows.
- Every successful password change/reset revokes all active refresh tokens; failed operations do not.
- If refresh-token revocation fails, the password update is rolled back; no partial password/session update is committed.
- A password-reset task passes the database kind constraint and dispatches to the reset-email job, never the image-resize job.
- Reset links put encoded user ID and token in the fragment, and the frontend submits them only in the reset POST body.
- The change-password form is hidden for accounts without a local password.
- Frontend provides login recovery, reset submission, and signed-in password-change entry points.

## Builder decisions

- Use the repository's current route naming, error mapping, and rate-limit conventions.
- Use the existing background-job retry and logging conventions for reset email delivery.
- Follow the existing frontend base-URL validation conventions for production HTTPS links.
